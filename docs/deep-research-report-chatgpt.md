# NVML and Power Measurement on GB10  
GB10 (Grace Blackwell) uses a unified 128 GB CPU/GPU memory pool, so standard NVIDIA NVML calls often fail. In practice, many NVML queries (especially memory info) return “Not Supported” on GB10【20†L15-L24】. For example, nvidia-smi and PyTorch GPU monitors cannot detect a discrete framebuffer, and Python’s pynvml library returns `NVML_ERROR_NOT_SUPPORTED`【20†L15-L24】. Tools like nvtop report *power usage* correctly (e.g. ~58 W)【1†L259-L262】, but memory usage and fan data show N/A【1†L259-L262】【20†L15-L24】. (The SoC’s GPU is connected via NVLink-C2C, not PCIe, which NVML may mislabel【1†L247-L254】.)  

In short, **nvmlDeviceGetPowerUsage** *does* work on GB10 for GPU power, but many other NVML metrics do not.  Community users have built a “NVML shim” to emulate missing features via CUDA runtime and `/proc/meminfo`【20†L34-L42】. For a hackathon, one can rely on NVML’s power readings or use NVIDIA’s CLI (e.g. `nvidia-smi`) to sample GPU power.  (For CPU/SoC power, one might use Linux perf counters or off-chip wattmeters; GB10 does *not* offer a tegrastats equivalent.) DGX Base OS is Ubuntu-based with standard Linux accounts, so you typically have root/sudo access to install tools or run GPU queries. Overall, NVML is the most direct method to measure GPU power on GB10, but note its limitations on memory reporting and that a shim or workaround may be needed for full telemetry【20†L15-L24】【1†L259-L262】.  

# OpenClaw: A Local AI Agent Framework  
OpenClaw is an open-source (MIT-licensed) “local-first” AI assistant framework【13†L553-L561】.  It runs as a Node.js gateway on your machine and can connect to **local LLMs** (via tools like LM Studio or Ollama) to provide chat/agent capabilities【17†L99-L107】. OpenClaw exposes a rich **Gateway API** (WebSocket and REST) that lets you programmatically send messages, manage sessions, and hook in external “tools” or skills【13†L553-L561】【30†L66-L74】. It integrates with many channels (Telegram, Slack, Discord, WhatsApp, etc.) and even has a web-based chat UI. In practice, you run `openclaw onboard` to install a daemon and then interact via CLI or web UI. An OpenClaw app can be extended via custom “tools”: for example, it supports an OpenAI-compatible `/v1/chat/completions` endpoint and a `/api/tools/invoke` interface for HTTP tool calls【30†L139-L148】. 

Because OpenClaw is **self-hosted and extensible**, it’s well-suited as a building block for an LLM app with energy instrumentation. You could plug in a local model (e.g. Nemotron via llama.cpp) and then add a custom “tool” or skill that calls NVML or the Neuralwatt API to fetch power/energy metrics. The agent’s responses (in chat or the UI) could then include those metrics. In other words, OpenClaw provides the conversation layer and plugin hooks, and you can insert energy-measurement code as a new skill/tool. (All code runs locally, preserving privacy and control.) 

# Available LLMs on GB10 and Their Performance  
The GB10’s 48-SM Blackwell GPU (~RTX 5070 class) and 128 GB unified memory can handle up to ~40 GB VRAM–heavy models. For example, NVIDIA’s **Nemotron-3-Nano-30B-A3B** (a 30B-parameter MoE with 3B active) requires about ~38 GB VRAM【34†L129-L137】. Benchmarks on GB10 show **Nemotron-30B** achieving ~72 tokens/sec (quantized)【40†L81-L89】. Alibaba’s **Qwen3.5-30B** (a 30B model) runs ~57 tokens/sec under similar settings【40†L81-L89】. By contrast, very large open models run much slower: community reports suggest a 120B model (GPT-OSS-120B, quantized to MXFP4) runs on GB10 at only ~15 tok/s (versus ~50+ tok/s on an M2 Mac【38†L343-L351】).  

In practice, **30B-class open models** (Nemotron, Qwen3.5) are recommended for GB10, as they balance quality and speed. Smaller models (e.g. Mistral 7B, Llama2-13B) would run even faster (hundreds of tok/s) but may lack the same accuracy. Larger models (e.g. Llama2-70B, Falcon-40B) could be forced into memory via CPU/GPU offload but would be slow (~10–30 tok/s). In short, expect 30–70 tok/s for ~30B models (with mixed precision) on GB10【40†L81-L89】, and reserve >40 GB VRAM for them【34†L129-L137】. 

# Eco-Impact MVP Idea: Energy-Aware Chat UI  
The most buildable Eco-themed demo is a simple **chat interface that reports energy usage per query**.  For example, host a local LLM (Nemotron-3-Nano via llama.cpp or Ollama) on the Spark, and wrap each user prompt/LLM response with power measurements. We would poll NVML (or `nvidia-smi`) to log GPU power over the inference period【48†L270-L278】. The UI (could be a web page or CLI output) shows the AI’s answer *plus* an “energy receipt” like “Took **X mWh** (Y tokens/Joule) for this response.” This makes the hidden cost of AI tangible to users. An MVP could be as simple as a web chat with an added footer line per answer. Key risks include synchronizing NVML sampling with inference (ensuring start/end timestamps and averaging power to compute energy) and handling any metric latency. Alternatively, one could call the Neuralwatt hosted inference API (if internet is allowed) to get built-in energy stats, but this offloads computation off-device. Given 6 hours, a prototype might use Python’s `pynvml` (or a subprocess to `nvidia-smi`) to grab power *before* and *after* the model call and compute energy.  We would keep the UI minimal (perhaps a text interface or lightweight web app) to focus on measurement accuracy. 

# Integrating Energy Metrics into OpenClaw  
A natural way to add energy observability in OpenClaw is via a custom **tool/skill** that queries power metrics. OpenClaw’s Gateway API allows defining tools (invokable via `/api/tools/invoke`) that the agent can call【30†L139-L148】. We could write a tool (in Node.js or via shell) that uses NVML (or calls a Python script) to return current power draw or accumulated energy. Then, after the LLM generates a response, the agent can invoke this tool and append the result to its reply. For example, an agent message might end with: “*(Energy used: 0.12 Wh = 8.6 tok/J)*”. In the OpenClaw web UI or Discord interface, this could appear as an additional line or emoji indicator. If using Neuralwatt’s API instead, we could configure OpenClaw’s OpenAI-compatible endpoint to point to the Neuralwatt URL (just as NVIDIA’s NIM can be used via a custom base URL). Either way, the UX is: the user asks a question, gets a normal answer, and sees an explicit energy-cost annotation. Optionally, one could extend the web UI (which OpenClaw already provides for chatting) with a sidebar or status bar that shows real-time GPU power or cumulative energy—though that’s more work. The simplest is textual: treat energy info as part of the chat response. This leverages OpenClaw’s extension points without modifying its core UI, just adding a new “energy” tool and having the agent include its output.

# Existing Tools and Differentiation  
A few open-source projects target LLM energy measurement. For instance, **CodeCarbon** and **CarbonTracker** are libraries that wrap model inference and log GPU power (via NVML) and CPU power (via RAPL)【48†L259-L262】【48†L270-L278】.  There is also the ML.ENERGY Benchmark (GitHub: ml-energy/leaderboard) which automates running models and computing joules per response【50†L130-L138】. Soham Poddar’s “LLM-energy-benchmark” repository (NAACL 2025) provides scripts that use NVML (via `nvidia-smi`) to record energy during inference【48†L259-L262】. However, these tools are research/benchmark oriented, not end-user apps. They require writing experiments or long scripts, and typically report total joules after the run.  **No widely-used, user-friendly tool** currently exists that measures *per-query* energy on a local GPU and displays it in real time. Our project would differ by being interactive and UI-driven: it would plug into an AI chat loop and give immediate feedback. In other words, we’d repurpose NVML (as others do) but focus on a quick UI demo that highlights energy. That front-end focus—“show the energy cost of your last question” in a hackathon app—is what sets it apart from existing benchmarks.
